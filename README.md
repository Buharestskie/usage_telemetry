# usage_telemetry

## Назначение

Отвечает на вопрос «каким приложением и каким его разделом пользуются живые
люди». Нужен, чтобы отличить приложение, висящее мёртвым грузом, от
приложения, которым пользуются редко, но по делу, — и выключать первое, не
задев второе.

Состоит из двух частей: пакета, который встраивается в приложения и считает
обращения, и коллектора, который эти обращения принимает, хранит и сводит по
дням. Витрина — дашборд Grafana, он живёт в репозитории `infra`.

## Как это работает

```
приложение (middleware) ──пачками по HTTP──> коллектор ──> PostgreSQL
                                                              │
                                              суточные своды ──┤
                                                              ▼
                                                        Grafana (SQL)
```

Middleware вешается на приложение одной строкой и на каждое обращение
складывает событие в очередь в памяти. Фоновая задача раз в несколько секунд
отправляет накопленное пачкой. Обработчик запроса ничего не ждёт: если
коллектор недоступен, события **молча выбрасываются**, а если очередь
переполнилась — сбрасывается целиком. Телеметрия не имеет права влиять на
работу приложения, которое считает.

Коллектор складывает сырые события в PostgreSQL и раз в час пересчитывает два
суточных свода: людей по дням (человеко-дни) и разделы по дням. Сырьё живёт
90 дней и чистится, своды остаются навсегда — они занимают копейки и дают
историю, по которой можно сказать «этим стали пользоваться вдвое меньше», не
начиная новое наблюдение.

Единица счёта — **человеко-день**: пара «день + человек». Не сессии по
таймауту: на шкале «живое / мёртвое» человеко-дни устойчивее и не порождают
спора о методике в тот момент, когда кто-то не согласится с выключением
своего приложения.

## Возможности

- Учёт обращений в приложениях на FastAPI и Starlette — одной строкой.
- Учёт входящих сообщений и нажатий кнопок в ботах на aiogram.
- Шаблон пути вместо сырого адреса: `/api/deals/{id}`, а не две тысячи строк
  по одной на сделку.
- Идентификатор пользователя из той авторизации, которая в приложении уже
  есть: сессия в Redis, JWT виджета, `initData` бота.
- Отсечение шума на входе: статика, `OPTIONS`, проверки живости и метрики.
- Признак того, чем запрос аутентифицирован, — чтобы отделить человека от
  вызова между сервисами при разборе, а не на входе.
- Инициализация GlitchTip: у 21 проекта из 41 SDK сейчас нет вовсе.
- Суточные своды, чистка сырья и справочник человеческих имён приложений.

## API коллектора

Приём событий:

```bash
curl -s http://127.0.0.1:8130/events \
  -H 'Content-Type: application/json' \
  -d '{"events":[{"at":1790000000.0,"service":"dashboard_mpp2","source":"http",
       "method":"GET","path":"/api/deals/{id}","status":200,"duration_ms":12,
       "auth":"session","user_id":"3157","session_id":"s1","user_agent":"Mozilla/5.0"}]}'
```

```json
{"accepted":1}
```

Проба для мониторинга:

```bash
curl -s http://127.0.0.1:8130/health
```

```json
{"status":"ok"}
```

Сводка для человека:

```bash
curl -s http://127.0.0.1:8130/stats
```

```json
{"events":184203,"services":21,"oldest":"2026-09-22T09:14:03+00:00",
 "last_aggregate":{"started_at":"2026-09-22T13:00:01+00:00","rows_users":412,
                   "rows_paths":2180,"deleted":0}}
```

## Конфигурация

Пакет в приложении:

| Переменная | Обязательна | Что означает | Пример |
|---|---|---|---|
| `TELEMETRY_SERVICE` | да | Машинный код приложения. Должен совпадать с `project` в `status_page_services`, иначе на дашборде не подставится человеческое имя | `dashboard_mpp2` |
| `TELEMETRY_URL` | да | Адрес коллектора | `http://127.0.0.1:8130` |
| `TELEMETRY_ENABLED` | нет | Выключатель. `0` гасит сбор целиком | `1` |
| `TELEMETRY_QUEUE_SIZE` | нет | Предел очереди в памяти; при переполнении она сбрасывается целиком | `5000` |
| `TELEMETRY_BATCH_SIZE` | нет | Сколько событий уходит одной пачкой | `200` |
| `TELEMETRY_FLUSH_SECONDS` | нет | Через сколько отправлять неполную пачку | `5` |
| `TELEMETRY_TIMEOUT` | нет | Таймаут запроса к коллектору | `3` |
| `SENTRY_DSN` | нет | Адрес GlitchTip; без него отправка ошибок молчит | `https://…@monitoring.donula26.ru/42` |

Коллектор:

| Переменная | Обязательна | Что означает | Пример |
|---|---|---|---|
| `COLLECTOR_DSN` | да | Адрес базы. Без него коллектор не стартует | `postgres://telemetry:…@db:5432/telemetry` |
| `COLLECTOR_TZ` | нет | Часовой пояс, по которому режутся сутки в сводах | `Europe/Moscow` |
| `COLLECTOR_RETENTION_DAYS` | нет | Сколько держать сырые события | `90` |
| `COLLECTOR_AGGREGATE_WINDOW_DAYS` | нет | За сколько последних суток пересчитывать своды | `3` |
| `COLLECTOR_AGGREGATE_INTERVAL` | нет | Как часто гонять свод, секунды | `3600` |
| `COLLECTOR_MAX_BATCH` | нет | Предел размера принимаемой пачки | `1000` |
| `COLLECTOR_SERVICES_FILE` | нет | Справочник имён приложений, раскладывается Ansible | `/etc/telemetry/services.json` |

## Локальный запуск

Проверки пакета не требуют ни базы, ни сети:

```bash
python tests/test_telemetry.py
```

Проверки коллектора требуют настоящий PostgreSQL — своды, перцентиль и чистка
на подделке базы не проверяются. Тест работает в отдельной схеме и удаляет её
за собой, поэтому его можно гонять и против боевой базы:

```bash
COLLECTOR_TEST_DSN=postgres://telemetry:пароль@127.0.0.1:5433/telemetry python collector/tests/test_collector.py
```

Поднять коллектор целиком:

```bash
cd collector && POSTGRES_PASSWORD=локальный docker compose up --build
```

Встроить в приложение:

```python
from usage_telemetry import install_telemetry, mark_user

app = FastAPI()
install_telemetry(app)
```

И в зависимости авторизации, где сессия уже разобрана:

```python
mark_user(request, user_id=session.amocrm_user_id, auth="session")
```

В боте:

```python
from usage_telemetry import install_bot_telemetry

install_bot_telemetry(dispatcher)
```

## Деплой

Коллектор раскатывается ролью `telemetry_collector` из репозитория `infra` на
хост `global`:

```bash
ansible-playbook playbooks/telemetry_collector.yml
```

Роль забирает код из этого репозитория, выпускает самоподписанный сертификат
для TLS, разворачивает compose и раскладывает справочник приложений из
`status_page_services`. Пароль базы берётся из `telemetry_collector_db_password`
в Ansible Vault; без него роль останавливается с объяснением.

Приложения получают пакет строкой в `requirements.txt` и две переменные
окружения в своём compose. Раскатка по парку идёт одним окном обслуживания.

## Подводные камни

- **События теряются осознанно.** При недоступности коллектора или
  переполнении очереди пачка выбрасывается без повторов. Это выбор в пользу
  приложения: дашборд с дырой лучше, чем дашборд, который лежит.
- **Приложение, которое молчит, и приложение, которым не пользуются, выглядят
  одинаково.** Различить их можно только по справочнику ожидаемых приложений
  и отметке о первом событии — на дашборде для этого отдельная колонка. Пока
  число «сбор не раскатан» не ноль, выводы о неиспользуемых делать рано.
- **Строка запроса не пишется нигде** — ни в событии, ни в журнале nginx. В
  ней ходят разовые токены презентаций и ключи абонентского приложения, и
  хранилище с ретенцией 90 дней не должно превращаться в базу утёкших
  секретов. По той же причине не пишется referer.
- **`TELEMETRY_SERVICE` должен совпадать с `project` в `status_page_services`.**
  Не совпал — приложение появится на дашборде под машинным кодом и не попадёт
  в список ожидаемых.
- **Справочник имён читается только при старте.** Переименование приложения в
  инвентаре требует перезапуска коллектора; роль делает это сама.
- **Базе нужен TLS.** Grafana ходит в неё между серверами разных провайдеров
  по открытой сети. Сертификат самоподписанный, клиент подключается с
  `sslmode=require`: шифрование обязательно, имя узла не проверяется.
- **`Dispatcher` есть не у каждого бота.** `success_payment_bot` и
  `autoexcel_judge` — односторонние трубы доставки, входящих от людей у них
  нет, и мерить там нечего. Прочтения сообщений Telegram ботам не отдаёт.
